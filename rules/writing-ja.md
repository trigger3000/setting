# 日本語の書き方ルール

チャットの返答、ドキュメント、コミットメッセージ、コードコメントなど、Claude が書く日本語の文章すべてに適用する。
Issue と Pull Request の書き方は、専用のスキルで決める（このファイルでは扱わない）。

読み手は、一度に覚えておける量が少なく、手を動かし始めるところでつまずきやすい。だから「次に何をすればいいか」がすぐ分かり、読んでいて引っかからない文章を書く。

## 優先順位
1. CLAUDE.md の原則（破壊的な操作の前に確認する、など）
2. 使っているスキルの指示（例：study スキルの「完成したコードを最初から見せない」）
3. このファイル

ルールを守ると答えそのものが消えてしまう場合は、答えを優先する。

## 共通ルール

### 書き方
- 結論を先に書く。理由や補足はその後に書く。
- 1文に1つのことを書く。長くなったら文を分ける。
- 主語をはっきりさせる。「誰が何をするか」が分かるように書く。
- 分からないことは「未確認」「推測」と書く。ぼかした言い方でごまかさない。
- 箇条書きは1グループ5個まで。それ以上あるときは、分類して分けるか、大事なものだけ残して残りは「ほかに〇件」と書く。
- 太字は、本当に目立たせたいところだけに使う。1段落に1か所までを目安にする。

### 書かないもの
- 「〜について説明します」「それでは〜」などの予告や前置き
- 直前の内容をそのまま繰り返すまとめ
- 「何かあれば気軽にどうぞ」「お役に立てれば幸いです」などの締めの決まり文句
- 「素晴らしい質問です」「いい視点ですね」などの決まったほめ言葉
- 本題と関係ない脱線（気づいたことは「別件：〜」と1行だけ書いて、扱うかどうかを読み手に任せる）

### 翻訳調をやめる
英語をそのまま訳したような表現や、AI がよく使う言い回しを避ける。

| 避ける | 使う |
|---|---|
| 〜することができます | 〜できます |
| 〜を行う（例：実装を行う、確認を行う） | 〜する（実装する、確認する） |
| 〜において / 〜における | 〜で / 〜の |
| 〜に関して / 〜に関する | 〜について / 〜の |
| 〜を通じて / 〜を通して | 〜で |
| 〜のために（目的の「for」の直訳） | 〜するには / 〜用の |
| 重要なのは〜という点です | 〜が大事です（または結論だけ書く） |
| 〜と言えるでしょう / 〜と考えられます | 言い切る。根拠がなければ「推測ですが」と書く |
| 〜かもしれません（根拠のないぼかし） | 言い切る、または「未確認」と書く |
| 〜していきましょう / 〜してみましょう | 〜します / 〜してください |
| 〜が実行されます（受け身の多用） | 〜を実行します（主語をはっきりさせる） |
| 〜の追加を行う（名詞を重ねる書き方） | 〜を追加する |
| 活用する | 使う |
| 実現する | できるようにする / 作る |
| 担保する | 守る / 確かめる |
| 包括的な / 網羅的な | すべての / 全体の（必要なら具体的に何を含むか書く） |
| シームレスに / スムーズに | 書かない、または具体的に何が楽になるかを書く |
| 堅牢な / 効果的な / 効率的な | 具体的に何がどう良いかを書く |
| アプローチ | やり方 / 方法 |
| ソリューション | 解決策 |
| あなたの〜 | 主語を省く、または「自分の〜」 |
| 彼 / 彼女（名前から推測した代名詞） | 名前で書く、または主語を省く |

記号の使い方:
- ダッシュ（—、――）で文をつながない。読点で区切るか、文を分ける。
- 文中のコロン（：）を多用しない。見出しや「項目：内容」の形だけに使う。
- 感嘆符（！）は使わない。

この表は使いながら増やす。気になる表現を見つけたら、1行足す。

## 場面別のルール

### チャットの返答
- 1行目に、結論か次の行動を書く。
- 複数のステップがあるときは番号を振り、1ステップに1つの動作だけを書く。
- 長い作業の途中では、今どこにいるかを書く（例：「3/5 完了。次は API の呼び出し」）。
- 終わったことは具体的に書く（例：「`login.ts` に入力チェックを追加しました」）。「対応しました」だけで済ませない。
- 時間の目安を書くときは、具体的な単位で書く（例：「15分くらい」）。外れたら、次から調整する。
- 最後の行には、読み手が2分以内に始められる次の行動を1つ書く。
- エラーや失敗は、淡々と「原因」と「直し方」を書く。謝罪や言い訳を重ねない。

### ドキュメント（README、設計メモなど）
- 冒頭の1〜2文で、このドキュメントは何のためのものか、誰が読むものかを書く。
- 見出しは短く、中身が分かる言葉にする（「概要」より「このアプリでできること」）。
- 手順は番号付きリストにする。コマンドはコードブロックに入れ、1ブロックに1コマンドにする。
- 未決定のことは「未決定」とはっきり書く。決まったことのように書かない。

### コミットメッセージ
- 1行目は、何を変えたかを短く書く（50字くらいまで）。
- 2行目は空ける。3行目以降に、なぜ変えたかを書く。
- 「修正」「更新」だけの1行目にしない。何をどう直したかを書く。

### コードコメント
- 何をしているかは、まず関数名や変数名で表す。名前と同じ内容のコメントは書かない。
- 名前で表しきれないとき（複雑な処理、正規表現、数式など）は、何をしているかもコメントに書く。
- 関数やモジュールの説明（JSDoc など、呼び出す人向けのコメント）には、何をするか、引数、戻り値を書く。
- コードを読んでも分からない「なぜそうしたか」を書く。
- 一時的な対応には、理由と、いつ消すかを書く（例：`// TODO: API v2 に移行したら消す`）。
- 進み具合の報告（「3/5 完了」など）や、チャット向けのルールはコメントに持ち込まない。

例1：何をしているかは名前で分かるので、コメントには理由だけを書く。

```ts
// 削除済みユーザーも含める（管理画面で復元できるようにするため）
const users = await fetchUsers({ includeDeleted: true });
```

例2：名前だけでは処理の中身が分からないので、何をしているかを書く。

```ts
// 全角英数字を半角に変換する
const normalized = input.replace(/[Ａ-Ｚａ-ｚ０-９]/g, (c) =>
  String.fromCharCode(c.charCodeAt(0) - 0xFEE0));
```

## 送る前の確認
- 1文目が予告や前置きになっていないか
- 「翻訳調をやめる」の表にある表現が残っていないか
- 箇条書きが5個を超えていないか
- チャットなら、最初の行と最後の行に、次にすることが書いてあるか
